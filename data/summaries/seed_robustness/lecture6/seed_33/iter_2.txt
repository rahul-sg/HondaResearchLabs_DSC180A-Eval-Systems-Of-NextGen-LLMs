This lecture examined **nested SQL queries**—queries that include other queries—and explained how their structure, logical behavior, and monotonicity affect correctness and optimization potential. It built on prior coverage of SQL features such as projections, selections, joins, aggregates, grouping, and updates.

A **subquery** may return a single value or a full relation and can appear in a **SELECT**, **FROM**, or **WHERE** clause. The slides emphasized a key principle: **avoid nested queries when possible**, not purely for performance but because they can often be rewritten more clearly and efficiently as joins. However, some cases, particularly involving logical quantifiers, **cannot be unnested**.

Subqueries in the **SELECT clause** illustrated correlated subqueries, where values from an outer query are used inside the inner one (e.g., computing a movie’s genre or average actor salary). Equivalent join-based formulations, called **subquery unnesting**, were shown to yield the same results in many cases, though differences can emerge when outer joins or NULL values are involved. Subqueries in the **FROM clause** demonstrated how intermediate results can be expressed as derived tables or **common table expressions (CTEs)**, effectively refactoring a query for clarity while producing the same output.  

Subqueries in the **WHERE clause** introduced **logical quantifiers**. The **EXISTS** and **IN** operators express **existential quantifiers**, testing whether related tuples exist or belong to a set. These constructs align closely with join semantics and can be rewritten as equivalent join queries. In contrast, **universal quantifiers** (“for all”) are more complex because SQL lacks direct syntax for them. The lecture showed how universal logic can be simulated using **NOT IN** or **NOT EXISTS**, such as retrieving actors who acted only in action movies or movies where every actor’s salary exceeds $100K. These examples illustrated multi-step reasoning: first identifying disqualifying records (e.g., non-action actors), then excluding them.  

The final section connected subquery behavior to **monotonicity**. A query is **monotone** if adding more tuples to input tables never removes results from the output; queries without subqueries or aggregates satisfy this property. The slides outlined a proof using **nested loop semantics**, noting that inserting a tuple in any relation cannot eliminate an existing result. **Monotone queries can be unnested**, whereas **non-monotone queries**—those involving negation, universal quantifiers, or aggregation—cannot. This theoretical link clarifies both the feasibility and limits of optimizing nested SQL queries.
