This lecture examined **nested SQL queries**—subqueries embedded within other queries—and their connection to **monotonicity**, which determines whether these nested forms can be safely “unnested” into flat SELECT‑FROM‑WHERE structures. Building on earlier SQL operators (projections, selections, joins, aggregates, grouping, and modification commands), it defined a **subquery** as a query appearing inside a **SELECT**, **FROM**, or **WHERE** clause. Subqueries can yield single values, relations, or sets used in comparisons. A guiding rule noted on the slides was: *avoid nested queries when possible*, though in some cases they are necessary for expressing dependencies between computed tables.

Under **subqueries in the SELECT clause**, the lecture illustrated *correlated subqueries*—where the inner query refers to the outer one. Examples included retrieving each actor and the genre of their movie, counting the number of actors in each film, and computing the average actor salary for movies with rating > 9. Each nested form was shown alongside an equivalent un‑nested version using joins and GROUP BY, demonstrating *subquery unnesting*. Slide comparisons asked whether these rewritten forms were logically equivalent, emphasizing that logical equivalence—not performance—motivates unnesting.

**Subqueries in the FROM clause** created derived tables (inline views). The lecture showed how a subquery could be given an alias and queried again, or replaced with a **common table expression (CTE)** using `WITH`. This “subquery refactoring” preserves semantics while clarifying query structure. Equivalent join‑based rewrites demonstrated that such subqueries often add no new expressive power.

For **subqueries in the WHERE clause**, the lecture introduced **logical quantifiers**. *Existential quantifiers* (“there exists”) use **EXISTS** or **IN** to test set membership, as when finding actors who appeared in some Sci‑Fi movie. These often translate into join queries. *Universal quantifiers* (“for all”) require negation, using **NOT IN** or **NOT EXISTS**; examples included retrieving actors who acted only in Action movies or movies where all actors earn over $100K. Such forms are harder to unnest because they rely on negated or quantified conditions.

The lecture concluded with **monotone versus non‑monotone queries**. A SELECT‑FROM‑WHERE query without subqueries or aggregates is *monotone*—adding tuples to input tables never removes output tuples, as shown via nested‑loop semantics. From this, the slides stated:  monotone queries can be unnested, whereas *non‑monotone* ones—those involving negation, aggregation, or universal quantifiers—cannot. This logical distinction explains why some nested SQL queries are inherently non‑unnestable.
