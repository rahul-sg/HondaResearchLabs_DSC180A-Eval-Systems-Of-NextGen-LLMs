This lecture focused on **nested SQL queries**—subqueries embedded inside other queries—and their connection to **monotonicity**, which governs when such queries can be simplified through *unnesting*. Building on earlier SQL features (projections, selections, joins, aggregates), it defined a subquery as a query that can appear within the **SELECT**, **FROM**, or **WHERE** clauses. Subqueries can yield single values, full relations, or sets of values used for comparison. The lecture emphasized a key principle: *avoid nested queries when possible*, since most can be rewritten into equivalent join‑based forms, though some conditions make nesting necessary.

Under **subqueries in the SELECT clause**, examples showed correlated subqueries that return related data—such as the genre of each movie an actor appears in, the number of actors per movie, or the average actor salary for movies rated above 9. Equivalent “unnested” versions used joins and GROUP BY for efficiency. However, the slides stressed that unnesting may change semantics when outer joins are involved: for instance, an inner‑join rewrite can omit rows preserved by a left outer join. Thus, SQL rewriting must respect join type as well as filtering context.

**Subqueries in the FROM clause** acted as derived tables or inline views, producing intermediate results that can be queried again. These were paralleled by *common table expressions (CTEs)*, demonstrating “subquery refactoring” that retains meaning while improving readability.  

**Subqueries in the WHERE clause** illustrated logical quantifiers. *Existential quantifiers* (“there exists”) were expressed using **EXISTS** or **IN**, to test if related records meet some property—such as identifying actors who played in a Sci‑Fi movie. These can often be unnested using joins. *Universal quantifiers* (“for all”) required negation, implemented through **NOT IN** or **NOT EXISTS**, as in finding actors who acted only in Action movies or movies where all actors’ salaries exceed \$100K. Because such constructs rely on negated or multi‑step conditions, they are harder to simplify.

The lecture concluded with **monotone versus non‑monotone queries**. Using nested‑loop semantics, it established that a **SELECT‑FROM‑WHERE** query *without subqueries or aggregates* is monotone—adding tuples to input relations never removes outputs. From this, it followed that monotone queries can be safely unnested, whereas non‑monotone ones—those involving negation, aggregation, or universal quantifiers—cannot. This theoretical principle explains why certain SQL subqueries inherently resist unnesting.
