This lecture extended earlier SQL concepts—projections, selections, joins, grouping, and aggregation—by focusing on **nested SQL queries (subqueries)**: queries embedded within another query. It outlined where subqueries can appear—**SELECT**, **FROM**, and **WHERE** clauses—and what they can return, from a single value to an entire relation. A general rule of thumb stressed avoiding unnecessarily nested queries when equivalent flat forms exist.

In the **SELECT clause**, examples showed subqueries computing the genre for each actor’s movie, counting actors per film, or finding the average salary in high‑rated movies. These illustrated **correlated subqueries**, which reference outer‑query variables and can yield multiple results. Through **subquery unnesting**, such correlated forms were rewritten as joins or grouped aggregations. However, Slide 10 emphasized that not all rewrites are identical: replacing nested queries with inner joins versus left outer joins may alter results when some movies have no matching `ActedIn` tuples, so equivalence must be checked explicitly.

Subqueries in the **FROM clause** served as intermediate or temporary relations, simplifying step‑wise logic such as filtering on rating ranges. The lecture also showed how the same logic can be expressed through **common table expressions (WITH clauses)**. These non‑correlated subqueries can typically be flattened into equivalent single‑level queries by unnesting without changing semantics.

Subqueries in the **WHERE clause** connected SQL to logic through quantifiers. **Existential quantifiers**—implemented with `EXISTS` or `IN`—test if related records exist, paralleling inner‑join behavior (e.g., finding actors in Sci‑Fi movies). **Universal quantifiers**—interpreted as “for all” or “every”—require more elaborate expressions. Because SQLite does not support `ALL`, they were represented with negation forms like `NOT IN` or `NOT EXISTS`: for example, identifying actors who acted only in action movies, or movies whose actors all earn above \$100K. Stepwise construction helped illustrate how identifying disqualifying tuples first allows expressing universal conditions via negation.

The lecture closed by contrasting **monotone** and **non‑monotone** queries. A *monotone* query’s output never shrinks when input data grows. A theorem established that any plain SELECT–FROM–WHERE query without subqueries or aggregates is monotone and therefore can be safely unnested. By contrast, queries containing negation, universal quantifiers, or aggregates—such as the `NOT IN` example on Slides 30–32—are *non‑monotone*, meaning unnesting them can change results. This logical property provides the theoretical basis for determining when nested SQL queries may or may not be transformed.
