This lecture covered **nested SQL queries**, describing how **subqueries** appear in the **SELECT**, **FROM**, and **WHERE** clauses, when they can be **unnested**, and how they relate to logical **quantifiers** and **query monotonicity**. Building on earlier SQL operations (projections, selections, joins, aggregates, grouping, and updates), it defined a subquery as a query embedded in another query and emphasized a rule of thumb: *avoid nested queries when possible*, though some are unavoidable.

In the **SELECT clause**, examples used **correlated subqueries** to compute derived values—such as returning each actor’s movie genre, the average actor salary for highly rated movies, or the number of actors per movie. These nested forms can often be rewritten as equivalent join and `GROUP BY` queries through **subquery unnesting**. However, the slides questioned equivalence, showing multiple formulations (including one with a `LEFT OUTER JOIN`) to illustrate that not all rewritings yield identical results.

Subqueries in the **FROM clause** acted as **derived tables** or **common table expressions (CTEs)**. The lecture demonstrated applying a subquery to select movies with rating > 8, then filtering results with rating < 9. This non‑correlated example, described as **subquery refactoring**, improves clarity and produces the same result as a single combined filter.

Subqueries in the **WHERE clause** introduced logical **quantifiers**. Using `EXISTS` or `IN` implements **existential quantifiers**, which test for the presence of at least one record and can be replaced by equivalent joins. **Universal quantifiers** (“for all”) required complementary logic: first identify actors appearing in any non‑Action movie, then select those **not** in that set to find actors who acted only in Action films. Other examples used count‑based comparisons or forms like `< ALL` and `NOT EXISTS` to express universal conditions, such as ensuring all actors in a movie earned over $100 K.

The concluding section connected quantifiers to **query monotonicity**. A query is *monotone* if adding tuples to input relations cannot remove output tuples. The slides stated a formal result: **If Q is a SELECT‑FROM‑WHERE query without subqueries or aggregates, then it is monotone.** Monotonic queries can be safely **unnested**, while those involving negation, universal quantifiers, or aggregates are **non‑monotone**, meaning additional data can eliminate prior outputs. Thus, non‑monotone queries generally cannot be unnested.
