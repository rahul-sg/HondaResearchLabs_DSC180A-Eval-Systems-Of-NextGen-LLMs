This lecture explored **nested SQL queries**, explaining how subqueries function within different clauses and how their form affects both efficiency and semantics. Building on earlier topics—projections, selections, joins, grouping, and aggregation—it introduced **subqueries** as queries embedded inside others, possibly returning a single value or a relation. Subqueries can appear in the **SELECT**, **FROM**, or **WHERE** clauses, and the guiding principle is to **avoid nesting when possible**, though sometimes it is necessary to express certain conditions.

In the **SELECT clause**, subqueries were used to compute derived attributes such as a movie’s genre, the number of actors in a movie, or the average actor salary. These often involve **correlated subqueries**, which reference variables from the outer query. The lecture demonstrated **subquery unnesting**, showing that equivalent results can usually be obtained with joins and aggregation. However, equivalence depends on join type: an unnested version using an **inner join** may differ from one using a **left outer join**, as shown in the comparison of salary and rating queries on Slide 10. Thus, correctness—not just performance—must be verified when transforming queries.

Subqueries in the **FROM clause** defined intermediate results, either inline or using a **common table expression (CTE)**. This technique, termed *subquery refactoring*, created a temporary relation name for clarity but produced a query equivalent to a single flattened statement rather than altering logic.

Within the **WHERE clause**, subqueries captured logical quantifiers. Using `EXISTS` or `IN` expressed **existential quantifiers** (“there exists”), testing for tuple existence or set membership. These could be rewritten as joins and are conceptually straightforward. By contrast, **universal quantifiers** (“for all”) were harder to model directly. The lecture showed examples using `NOT IN` or `NOT EXISTS` to retrieve actors who acted only in action movies or movies where all actors’ salaries exceeded $100K, highlighting SQL’s indirect handling of universals.

Finally, the lecture introduced **monotone versus non‑monotone queries**. A query is *monotone* if adding tuples to input tables never removes results. Basic SELECT‑FROM‑WHERE queries without subqueries or aggregation are monotone and therefore safely **unnestable**. Queries employing **negation, aggregation, or universal quantifiers** are non‑monotone, so unnesting them can change outcomes. This theoretical link clarifies when and why nested queries can—or cannot—be rewritten safely.
