This lecture examined **nested SQL queries**, focusing on how subqueries operate within different clauses and the implications for efficiency, equivalence, and logic. Building on prior concepts—projections, selections, joins, grouping, and aggregation—it defined a **subquery** as a query embedded within another query. Subqueries can appear in the **SELECT**, **FROM**, or **WHERE** clauses and may return either a single value or a relation. The rule of thumb is to **avoid nesting whenever possible**, although some conditions require it.

In the **SELECT clause**, subqueries computed derived attributes such as a movie’s genre, the number of actors in a movie, or the average actor salary. Many of these were **correlated subqueries**, which reference values from the outer query. The lecture illustrated **subquery unnesting**, demonstrating that equivalent results can often be obtained with joins and aggregation. However, equivalence depends on join type: an unnested version using an *inner join* may differ from a *left outer join*, affecting rows with missing matches. Thus, both semantics and correctness must be checked when flattening subqueries.

Subqueries in the **FROM clause** produced intermediate results and could be labeled using **common table expressions (CTEs)**—a process known as *subquery refactoring*. These synthetic tables improved readability while preserving logical equivalence to a single-level query.

Subqueries in the **WHERE clause** introduced logical quantifiers. Using `EXISTS` or `IN` represented **existential quantifiers** (“there exists”), testing for tuple existence or set membership and corresponding to join operations. In contrast, **universal quantifiers** (“for all”) were more challenging to express in SQL. Examples included retrieving actors who only performed in action films or finding movies where *all* actors earned more than $100K. The attempted use of the `< ALL` construct—explicitly noted as *not supported in SQLite*—was replaced by a logically equivalent formulation using `NOT EXISTS`. These cases illustrated SQL’s indirect handling of universal conditions.

The lecture concluded with the concepts of **monotone and non‑monotone queries**. A query is monotone if adding tuples to input tables never removes existing results. Examples using tabular data showed that simple SELECT‑FROM‑WHERE joins remain *monotone*, whereas queries with `NOT IN` filters lose tuples when new data is added, making them *non‑monotone*. The final theorem established that SELECT‑FROM‑WHERE queries without subqueries or aggregation are monotone. Consequently, **only monotone queries can be safely unnested**, while those involving negation, aggregation, or universal quantifiers cannot.
