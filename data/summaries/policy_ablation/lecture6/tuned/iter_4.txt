This lecture explored **nested SQL queries**, explaining how subqueries appear within different clauses and how their logic connects to optimization through *unnesting* and *monotonicity*. After a brief recap of core SQL features—projections, selections, joins, aggregates, grouping, and data modifications—it defined a **subquery** as a query inside another query. Subqueries can be placed in the **SELECT**, **FROM**, or **WHERE** clause, and while they can greatly increase expressiveness, the rule of thumb is to avoid nesting when equivalent results can be expressed more directly using joins. This transformation is known as *subquery unnesting*.

In the **SELECT clause**, examples showed subqueries returning single values or relations—for instance, listing each actor with the genre of their movie or computing the average actor salary for films rated above 9. Equivalent join-based rewrites were presented as more efficient. However, slides demonstrated that equivalence can break when outer joins are involved, because a left outer join includes movies even when no matching actor exists, altering query results.

Subqueries in the **FROM clause** act as *derived tables* that simplify complex filtering or rearrange logic. They can be named using *common table expressions (CTEs)*, which define subquery results up front for reuse. These are non‑correlated and can also be unnested without changing results.

The **WHERE clause** introduced subqueries as logical quantifiers. **Existential quantifiers**, implemented with *EXISTS* or *IN*, test whether at least one related tuple satisfies a condition—e.g., identifying actors who appeared in a Sci‑Fi movie. Such queries translate directly into join formulations. **Universal quantifiers** express conditions that must hold for *all* related tuples. The slides illustrated “only acted in Action movies” by first finding actors who appeared in any non‑Action movie, then excluding them. Another example sought movies whose actors all earned more than \$100K. The approach using `<ALL` demonstrates this logic but was noted as unsupported in SQLite; the equivalent form using `NOT EXISTS` was introduced specifically to handle this limitation.

The lecture concluded with **monotone queries**—those whose outputs never lose tuples when input data grow. The slides formalized this property (“whenever we add tuples… the answer will not lose any output tuple”) and showed side‑by‑side examples distinguishing monotone and non‑monotone behavior. Using nested‑loop semantics, any basic SELECT–FROM–WHERE query without subqueries, aggregates, or negation is monotone. The key takeaway is that **only monotone queries can be safely unnested**, while non‑monotone queries—those involving negation, aggregates, or universal quantifiers—cannot. (≈396 words)
