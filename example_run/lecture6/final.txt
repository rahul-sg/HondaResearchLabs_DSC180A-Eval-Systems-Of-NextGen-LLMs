This lecture deepened the study of SQL by focusing on **nested (sub)queries** and linking them to **logical quantifiers** and **query monotonicity**. After a brief recap of prior SQL features—projections, selections, joins, aggregates, grouping, and data modification—it defined a **subquery** as a query inside another query, which may appear in the **SELECT**, **FROM**, or **WHERE** clause. Subqueries can return either single values or full relations and are particularly useful for expressing conditions that depend on computed results. The slides emphasized a key principle: **avoid nested queries when possible**, because many can be **unnested** into equivalent join or aggregation forms.  

In the **SELECT clause**, examples showed correlated subqueries that compute attributes such as movie genre, number of actors, or average salary. The lecture compared these to join-based rewritings, stressing **subquery unnesting**—rewriting a nested form into a standard join. However, slide 10 illustrated that not all transformations preserve semantics: an inner join and a left outer join may yield different results when null or missing matches occur. Thus, unnesting requires understanding when equivalence actually holds, not assuming it universally.

**Subqueries in the FROM clause** serve as derived tables or temporary views and can alternatively be expressed through **common table expressions (CTEs)**. The lecture referred to this as **subquery refactoring**, noting that such forms are usually straightforward to unnest without changing the output.

The **WHERE clause** section connected SQL to **logical quantifiers**. Using **EXISTS** or **IN** represents **existential quantifiers** (“there exists”), true when the subquery returns one or more tuples. These can typically be replaced with equivalent joins. **Universal quantifiers** (“for all”) lack direct SQL syntax but can be simulated. One example retrieved actors who acted **only in Action movies** by first identifying those linked to any non‑Action movie, then excluding them. Another example expressed “all actors in a movie earn above $100K” through a **NOT EXISTS** formulation.

Finally, the lecture introduced **monotone versus non‑monotone queries**. A query is **monotone** if adding tuples to input tables cannot remove tuples from the result. The theorem stated that a basic **SELECT‑FROM‑WHERE** query without subqueries or aggregates is monotone. Building on this, slide 34 noted that **monotonicity allows**, but does not guarantee, **unnesting** of nested queries. Conversely, queries using negation, universal quantifiers, or aggregates are **non‑monotone**, meaning unnesting is not possible.
